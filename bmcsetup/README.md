# Luna2 BMC Setup Backend for Open OnDemand

Python backend service for managing Luna2 BMC setup configuration from the TrinityX Open OnDemand interface.

This service sits between Open OnDemand and the Luna2 daemon. It exposes a small HTTP API that the future Vue.js frontend can call to list, create, update, clone, rename, delete and inspect BMC setup records.

```text
TrinityX
  └── Open OnDemand
        └── Luna2 BMC Setup Python Backend
              ├── Flask API: /api/v1/...
              ├── Token handling for Luna2 daemon
              └── Luna2 daemon REST API
                    └── BMC setup configuration

Future UI flow:
Open OnDemand page → Vue.js frontend → Python backend → Luna2 daemon
```

---

## 1. Purpose

The backend provides a BMC setup management API for Luna2 `bmcsetup` objects inside TrinityX Open OnDemand.

It is responsible for:

- serving the Open OnDemand application shell;
- exposing BMC setup related API routes for the frontend;
- reading Luna daemon connection details from the Luna configuration file;
- retrieving and caching a Luna daemon API token;
- forwarding BMC setup actions to the Luna2 daemon;
- returning a consistent frontend-friendly response where possible.

BMC setup records define the credentials and channel settings used by Luna to configure or interact with Baseboard Management Controllers.

## 3. Configuration

The backend reads Luna daemon API settings from the Luna configuration file defined by `INI_FILE`.

The expected configuration section is:

```ini
[API]
USERNAME=<luna-api-username>
PASSWORD=<luna-api-password>
SECRET_KEY=<jwt-secret-key>
PROTOCOL=https
ENDPOINT=<luna-daemon-host>:<luna-daemon-port>
VERIFY_CERTIFICATE=true
```

The backend also uses a `TOKEN_FILE` to cache the JWT token received from the Luna2 daemon. The token file is written with permission mode `0600`.

Before processing requests, the backend validates that:

- the Luna configuration file exists;
- the Luna configuration file is readable;
- the token file path is valid.

If this validation fails, the backend returns the Open OnDemand `error.html` template rather than a JSON API response.

When `APP_STATE` is `False`, the backend runs in development mode.

Development mode enables:

- Flask debug mode;
- CORS for `http://localhost:5173`;
- direct Flask serving on `0.0.0.0:7755`;
- optional SSL if the configured certificate and key files exist.

Development SSL paths used by the current code:

```text
/trinity/local/etc/ssl/vmware-controller1.cluster.crt
/trinity/local/etc/ssl/vmware-controller1.cluster.key
```

When `APP_STATE` is not `False`, the application starts with the default Flask `app.run()` behaviour and is expected to be served in the production Open OnDemand context.

## 5. General response format

Most API endpoints return the following JSON envelope:

```json
{
  "status": true,
  "status_code": 200,
  "content": {}
}
```

| Field | Meaning |
| --- | --- |
| `status` | Boolean success indicator generated by the backend wrapper. |
| `status_code` | Luna daemon status code or backend-generated status code. |
| `content` | Data or error details returned by the Luna daemon or backend. |

Important frontend note:

The Flask route itself often returns HTTP `200`, even when the JSON body contains an error such as `status: false` and `status_code: 404`.

For the Vue.js frontend, do not rely only on the HTTP response code. Always check:

```js
if (response.data.status === true) {
  // show success box
} else {
  // show failure box using response.data.content
}
```

Exceptions:

- `GET /` returns HTML.
- `GET /api/v1/license` returns text/HTML, not the standard JSON envelope.
- configuration validation errors return `error.html`.
- unknown routes return `error.html` with HTTP `200`.

## 6. BMC setup object structure

A BMC setup record is expected under:

```json
{
  "config": {
    "bmcsetup": {
      "<bmcsetup-name>": {
        "name": "<bmcsetup-name>",
        "username": "<bmc-username>",
        "password": "<bmc-password>",
        "userid": 2,
        "mgmtchannel": 1,
        "netchannel": 1
      }
    }
  }
}
```

Example BMC setup object:

```json
{
  "config": {
    "bmcsetup": {
      "default-bmcsetup": {
        "comment": null,
        "mgmtchannel": 1,
        "name": "default-bmcsetup",
        "netchannel": 1,
        "password": "<masked-password>",
        "unmanaged_bmc_users": null,
        "userid": 2,
        "username": "admin"
      }
    }
  }
}
```

The backend uses the first key below `config.bmcsetup` as the record name:

```python
name = next(iter(request_data["config"]["bmcsetup"]))
```

For predictable behaviour, send only one BMC setup record per create, update, clone or rename request.

### Field notes

| Field | Type | Notes |
| --- | --- | --- |
| `name` | String | BMC setup name. Should match the object key for add/update operations. |
| `username` | String | BMC user name. |
| `password` | String | BMC password. The frontend should mask this field by default. |
| `userid` | Integer | BMC/IPMI user ID. Commonly `2`. |
| `mgmtchannel` | Integer | Management channel value used by Luna/BMC tooling. |
| `netchannel` | Integer | Network channel value used by Luna/BMC tooling. |
| `unmanaged_bmc_users` | String/null/list | Optional field depending on daemon-side support. |
| `comment` | String/null | Optional operator note. |

Security note: BMC credentials are sensitive. The frontend should avoid displaying passwords in clear text, avoid logging submitted payloads, and should use masked password inputs.

## 7.6 Clone BMC setup

```http
POST /api/v1/clone
```

Clones an existing BMC setup record in Luna2.

Internally calls:

```text
POST <luna-daemon>/config/bmcsetup/<bmcsetup-name>
```

The backend derives `<bmcsetup-name>` from the first key below `config.bmcsetup` and sends the payload to the daemon with `action="clone"`.

The exact payload required by the Luna daemon depends on daemon-side clone semantics. Based on the rename pattern, the payload should contain the source BMC setup and a daemon-recognised field for the target clone name.

### Success message box

```text
BMC setup cloned successfully.
```

### Failure message box

```text
Could not clone BMC setup. Check the source setup, target name and daemon validation message.
```

### Request body example

Use the field expected by the Luna daemon for the new clone name. If the daemon uses `newbmcname`, the payload may look like this:

```json
{
  "config": {
    "bmcsetup": {
      "default-bmcsetup": {
        "newbmcname": "default-bmcsetup-copy"
      }
    }
  }
}
```

If the daemon expects a full target object, use this shape instead:

```json
{
  "config": {
    "bmcsetup": {
      "default-bmcsetup-copy": {
        "comment": "Cloned from default-bmcsetup",
        "mgmtchannel": 1,
        "name": "default-bmcsetup-copy",
        "netchannel": 1,
        "password": "<copied-or-new-password>",
        "unmanaged_bmc_users": null,
        "userid": 2,
        "username": "admin"
      }
    }
  }
}
```

### Success response example

The expected ideal backend response should be:

```json
{
  "status": true,
  "status_code": 201,
  "content": {
    "message": "BMC setup default-bmcsetup was cloned successfully."
  }
}
```

### Failure response examples

No JSON payload:

```json
{
  "status": false,
  "status_code": 400,
  "message": "No JSON payload received"
}
```

Daemon validation error:

```json
{
  "status": false,
  "status_code": 400,
  "content": {
    "message": "Invalid request: bmcsetup default-bmcsetup could not be cloned"
  }
}
```

### Backend implementation caveat

The application route exposes `POST /api/v1/clone`, but the `Rest.post_data()` implementation must explicitly handle `action == "clone"`.

If the `Rest.post_data()` logic is still the same as the Network backend version, clone success may be reported incorrectly because only these actions currently have explicit success handling:

- `add` with daemon HTTP `201`;
- `update` with daemon HTTP `204`;
- `rename` with daemon HTTP `204`.

Recommended backend addition:

```python
elif response.status_code in [200, 201, 204] and action == "clone":
    self.response = {
        "status": True,
        "status_code": 200 if response.status_code == 204 else response.status_code,
        "content": {"message": f"{table.capitalize()} {name} is cloned successfully."}
    }
```

If the daemon returns a JSON body on clone, preserve that JSON in `content` instead of replacing it with a generic message.

# 8. Frontend handling guide

## 8.1 Standard JSON API handling

For most API endpoints, the Vue.js frontend should check the JSON body:

```js
const result = await apiCall()

if (result.data?.status === true) {
  showSuccess(result.data.content)
} else {
  showFailure(result.data?.content || 'Request failed')
}
```

Do not treat HTTP `200` as success by itself.

The backend may return:

```json
{
  "status": false,
  "status_code": 404,
  "content": {
    "message": "Invalid request: bmcsetup missing-bmcsetup does not exist"
  }
}
```

with an outer Flask HTTP response of `200`.

## 8.2 Error message extraction

Recommended frontend message extraction:

```js
function getApiMessage(data, fallback = 'Request failed') {
  if (!data) return fallback

  if (typeof data.content === 'string') return data.content

  if (data.content?.message) return data.content.message

  if (data.message) return data.message

  return fallback
}
```

## 8.3 Password handling in the UI

BMC setup objects contain credentials. Recommended frontend behaviour:

- mask password values by default;
- do not show the current password in clear text in tables;
- use a dedicated password input for add/update forms;
- avoid writing request payloads containing passwords into browser logs;
- show only whether a password is configured, not the password itself;
- only send a password update when the user intentionally changes the field, if the daemon supports partial updates.

## 8.4 Suggested UI behaviour

| Action | After success | After failure |
| --- | --- | --- |
| List BMC setups | Render table/cards with password masked | Show error box and retry button |
| Add BMC setup | Show success box, refresh BMC setup list | Keep form values and show daemon message |
| Update BMC setup | Show success box, refresh selected BMC setup | Keep edit form open |
| Clone BMC setup | Show success box, refresh BMC setup list | Keep clone dialog open |
| Rename BMC setup | Show success box, refresh BMC setup list | Keep rename dialog open |
| Delete BMC setup | Show success box, refresh BMC setup list | Keep item visible and show error |
| Members | Render member list | Show empty/error state |
| Licence | Render licence text | Show fallback message |

# 10. Backend behaviour notes

These details matter for frontend implementation.

1. The backend is a wrapper around the Luna2 daemon. It does not store BMC setup data itself.
2. The backend retrieves daemon credentials from the Luna configuration file.
3. The backend requests a Luna daemon token and caches it in `TOKEN_FILE`.
4. If the cached token is invalid or expired, the backend requests a new token.
5. Create, update, clone and rename requests all call the Luna daemon with `POST` internally.
6. Delete calls the Luna daemon using the daemon-specific `_delete` route.
7. Member lookup calls the daemon-specific `_member` route.
8. The route method exposed to the frontend may differ from the method used internally against the Luna daemon.
9. Most API routes return JSON, but the application shell, licence route and configuration errors return HTML/text.
10. The frontend should refresh `/api/v1/bmcsetups` after add, update, clone, rename or delete actions.
11. The frontend should show daemon validation messages directly where possible because they explain the real reason for failure.
12. BMC passwords should be handled as sensitive data in the UI and logs.

```text
Body: <action-specific success message>
Style: green/positive state
Behaviour: auto-dismiss after a few seconds, except for destructive actions where keeping it visible can help confirmation
```

## Failure box

Use this for validation, daemon, configuration or connection errors.

```text
Title: Request failed
Body: <daemon message or backend fallback message>
Style: red/error state
Behaviour: keep visible until the user closes it or retries
```

The failure box should prefer messages in this order:

1. `content.message`
2. `content` when it is a string
3. `message`
4. generic fallback message

# 13. Known limitations and improvement points

These are not blockers, but they are useful to know before connecting the Vue.js frontend.

- Some error responses are JSON, while others are HTML/text.
- Some Flask routes return HTTP `200` even when the body contains an error status.
- `rename` returns a missing-payload error without `status_code`.
- `404` pages are rendered as `error.html` with HTTP `200`.
- Create, update, clone and rename assume one BMC setup object per request.
- The backend currently trusts the payload shape and passes validation mainly to the Luna daemon.
- The backend returns generated messages such as `Bmcsetup ...` because it uses `table.capitalize()`.
- If the `Rest.post_data()` implementation has not been updated for `action == "clone"`, the clone route may not return a correct success response even when the daemon accepts the request.
- Passwords are returned in the current `/api/v1/bmcsetups` response. The frontend should mask them, and the backend may later consider redacting them before sending data to the browser.

For a cleaner frontend contract later, consider standardising all API errors as JSON under the same envelope:

```json
{
  "status": false,
  "status_code": 400,
  "content": {
    "message": "Human-readable error message"
  }
}
```

A cleaner success message helper could also avoid `Bmcsetup` wording:

```python
DISPLAY_NAME = "BMC setup"
```

Then generate messages using `DISPLAY_NAME` instead of `table.capitalize()`.
