# Luna2 Cluster Backend for Open OnDemand

Python backend service for managing Luna2 **Cluster** configuration from the TrinityX Open OnDemand interface.

This service sits between Open OnDemand and the Luna2 daemon. It exposes a small HTTP API that the future Vue.js frontend can call to read, update and rename the main `cluster` configuration.

```text
TrinityX
  └── Open OnDemand
        └── Luna2 Cluster Python Backend
              ├── Flask API: /api/v1/...
              ├── Token handling for Luna2 daemon
              └── Luna2 daemon REST API
                    └── Cluster configuration

Future UI flow:
Open OnDemand page → Vue.js frontend → Python backend → Luna2 daemon
```

---

## 1. Purpose

The backend provides a Cluster configuration API for the Luna2 `cluster` object inside TrinityX Open OnDemand.

It is responsible for:

- serving the Open OnDemand application shell;
- exposing Cluster API routes for the frontend;
- reading Luna daemon connection details from the Luna configuration file;
- retrieving and caching a Luna daemon API token;
- forwarding Cluster update and rename actions to the Luna2 daemon;
- returning a consistent frontend-friendly response where possible.

The Cluster object defines global Luna settings such as the cluster name, controller information, DNS/NTP settings, provisioning behaviour, discovery behaviour and technical contact information.

Unlike the Network, BMC Setup, Switch and Other Device apps, this app manages a **single cluster-level configuration object** rather than a list of named records. Therefore, it does not provide `add`, `clone`, `delete` or `member` routes.

## 3. Configuration

The backend reads Luna daemon API settings from the Luna configuration file defined by `INI_FILE`.

The expected configuration section is:

```ini
[API]
USERNAME=<luna-api-username>
PASSWORD=<luna-api-password>
SECRET_KEY=<jwt-secret-key>
PROTOCOL=https
ENDPOINT=<luna-daemon-host>:<luna-daemon-port>
VERIFY_CERTIFICATE=true
```

The backend also uses a `TOKEN_FILE` to cache the JWT token received from the Luna2 daemon. The token file should be written with permission mode `0600`.

Before processing requests, the backend validates that:

- the Luna configuration file exists;
- the Luna configuration file is readable;
- the token file path is valid.

If this validation fails, the backend returns the Open OnDemand `error.html` template rather than a JSON API response.

## 4. Runtime modes

When `APP_STATE` is `False`, the backend runs in development mode.

Development mode enables:

- Flask debug mode;
- CORS for `http://localhost:5173`;
- direct Flask serving on `0.0.0.0:7755`;
- optional SSL if the configured certificate and key files exist.

Development SSL paths used by the current code:

```text
/trinity/local/etc/ssl/vmware-controller1.cluster.crt
/trinity/local/etc/ssl/vmware-controller1.cluster.key
```

When `APP_STATE` is not `False`, the application starts with the default Flask `app.run()` behaviour and is expected to be served in the production Open OnDemand context.

## 5. General response format

Most API endpoints return the following JSON envelope:

```json
{
  "status": true,
  "status_code": 200,
  "content": {}
}
```

| Field | Type | Description |
| --- | --- | --- |
| `status` | Boolean | Backend-level success flag. `true` means the backend considers the daemon request successful. |
| `status_code` | Number | Status code returned by the Luna2 daemon or generated by the backend. |
| `content` | Object/String | Response payload, daemon response, or error message. |

Important frontend note:

The Flask route usually returns HTTP `200` to the browser even when the Luna daemon operation failed. The Vue.js frontend should therefore check the JSON body, especially:

```js
response.data.status
response.data.status_code
response.data.content
```

Do not rely only on the HTTP status code returned by Flask.

The Cluster API returns a single `cluster` object under:

```text
content.config.cluster
```

Example response:

```json
{
  "content": {
    "config": {
      "cluster": {
        "controller": {
          "hostname": "vmware-controller1",
          "ipaddress": "10.141.255.254",
          "luna_config": "/trinity/local/luna/daemon/config/luna.ini",
          "serverport": 7050,
          "status": null,
          "vendor": null
        },
        "createnode_macashost": false,
        "createnode_ondemand": true,
        "debug": false,
        "domain_search": "cluster,ib,ipmi",
        "forwardserver_ip": "8.8.8.8,8.8.4.4",
        "name": "mycluster",
        "nameserver_ip": "10.141.255.254",
        "nextnode_discover": false,
        "ntp_server": "10.141.255.254",
        "packing_bootpause": true,
        "provision_fallback": "http",
        "provision_method": "torrent",
        "security": false,
        "technical_contacts": "root@localhost",
        "user": null
      }
    }
  },
  "status": true,
  "status_code": 200

```

### Field reference

| Field | Type | Description |
| --- | --- | --- |
| `name` | String | Cluster name. Used by the rename operation. |
| `controller.hostname` | String | Controller hostname. |
| `controller.ipaddress` | String | Controller IP address. |
| `controller.luna_config` | String | Path to the Luna daemon configuration file. |
| `controller.serverport` | Number | Luna daemon server port. |
| `controller.status` | String/Null | Optional controller status. |
| `controller.vendor` | String/Null | Optional controller vendor. |
| `createnode_macashost` | Boolean | Whether MAC addresses should be used as host references during node creation. |
| `createnode_ondemand` | Boolean | Whether node creation on demand is enabled. |
| `debug` | Boolean | Cluster debug setting. |
| `domain_search` | String | Comma-separated domain search list. |
| `forwardserver_ip` | String | Comma-separated forward DNS servers. |
| `nameserver_ip` | String | DNS nameserver IP address. |
| `nextnode_discover` | Boolean | Whether next-node discovery is enabled. |
| `ntp_server` | String | NTP server used by the cluster. |
| `packing_bootpause` | Boolean | Whether boot pause behaviour is enabled during packing/provisioning. |
| `provision_fallback` | String | Fallback provisioning method, for example `http`. |
| `provision_method` | String | Main provisioning method, for example `torrent`. |
| `security` | Boolean | Cluster security flag. |
| `technical_contacts` | String | Technical contact address or comma-separated addresses. |
| `user` | String/Null | Optional user field. |

### 8.5 Rename Cluster

Renames the Luna2 Cluster.

```http
PATCH /api/v1/rename
```

For Cluster rename, the backend expects the new cluster name in:

```text
config.cluster.name
```

Unlike the Network, BMC Setup, Switch and Other Device apps, the Cluster app does not use a field like `newnetname`, `newbmcname`, `newswitchname` or `newotherdevname`. It directly validates the new `name` value.

Payload structure:

```json
{
  "config": {
    "cluster": {
      "name": "newclustername"
    }
  }
}
```

Example:

```bash
curl -k -X PATCH https://vmware-controller1.cluster:7755/api/v1/rename \
```

## 9. Frontend implementation notes

### 9.1 Recommended frontend data loading flow

When the Vue.js frontend loads:

1. call `GET /api/v1/cluster`;
2. read `content.config.cluster`;
3. populate the Cluster settings form;
4. keep a local copy of the original payload;
5. on save, send the full updated `config.cluster` object to `PUT /api/v1/update`;
6. for rename, send only the required `config.cluster.name` value to `PATCH /api/v1/rename`, unless the daemon requires the full cluster object.

Example frontend mapping:

```js
const cluster = response.data.content.config.cluster

form.name = cluster.name
form.nameserver_ip = cluster.nameserver_ip
form.ntp_server = cluster.ntp_server
form.domain_search = cluster.domain_search
form.forwardserver_ip = cluster.forwardserver_ip
form.provision_method = cluster.provision_method
form.provision_fallback = cluster.provision_fallback
form.controller = cluster.controller
```

### 9.2 Always check backend response body

Because the Flask backend commonly returns HTTP `200`, the frontend should check the JSON body:

```js
if (data.status === true && data.status_code >= 200 && data.status_code < 300) {
  showSuccess(data.content?.message || 'Cluster operation completed successfully.')
} else {
  showError(data.content?.message || data.content || 'Cluster operation failed.')
}
```

### 9.3 Handle HTML errors separately

Configuration validation errors may return `error.html` instead of JSON. The frontend should handle non-JSON responses gracefully.

Recommended behaviour:

```text
If response content-type is JSON:
  parse and display API response.

If response content-type is HTML:
  show a generic backend configuration error.
```

Example message:

```text
The Cluster backend returned an HTML error page.
Check the Luna configuration file, token file and backend logs.
```

### 9.4 Table-level update caveat

The current Cluster app calls:

```python
Rest().post_data(TABLE, "", request_data, action="update")
Rest().post_data(TABLE, "", request_data, action="rename")
```

That means the shared `Rest.post_data()` method must support a blank `name` for table-level Cluster operations and should post to:

```text
/config/cluster
```

not:

```text
/config/cluster/<record>
```

If the shared `post_data()` implementation requires a non-empty `name`, the Cluster update and rename routes will fail. For this app, `name` must remain optional.

### 9.5 No add, clone or delete operations

The Cluster app intentionally exposes no routes for:

```text
POST   /api/v1/add
POST   /api/v1/clone
DELETE /api/v1/delete/<record>
```

The Cluster configuration is a singleton object, so the frontend should not show add, clone or delete actions for this app.

## 11. Validation recommendations

Frontend validation should happen before sending data to the backend.

Recommended checks:

- `name` must not be empty;
- `controller.hostname` must not be empty;
- `controller.ipaddress` should be a valid IPv4 or IPv6 address;
- `controller.serverport` should be a valid TCP port number;
- `nameserver_ip` should be a valid IP address;
- `ntp_server` should be a valid IP address or hostname;
- `forwardserver_ip` should be a comma-separated list of valid IP addresses;
- `domain_search` should be a comma-separated list of domain/search suffixes;
- boolean fields should be sent as real booleans, not strings;
- `provision_method` and `provision_fallback` should only allow known daemon-supported values.

Recommended frontend error message:

```text
Please check the highlighted Cluster settings before saving.
Some values are missing or not in the expected format.
```

## 12. Example frontend helper functions

### Load Cluster configuration

```js
async function loadCluster() {
  const response = await fetch('/api/v1/cluster')
  const data = await response.json()

  if (!data.status) {
    throw new Error(data.content?.message || 'Failed to load Cluster configuration')
  }

  return data.content.config.cluster
}
```

### Update Cluster configuration

```js
async function updateCluster(clusterPayload) {
  const response = await fetch('/api/v1/update', {
    method: 'PUT',
    headers: {
      'Content-Type': 'application/json'
    },
    body: JSON.stringify({
      config: {
        cluster: clusterPayload
      }
    })
  })

  const data = await response.json()

  if (!data.status) {
    throw new Error(data.content?.message || data.content || 'Failed to update Cluster configuration')
  }

  return data
}
```

### Rename Cluster

```js
async function renameCluster(newName) {
  const response = await fetch('/api/v1/rename', {
    method: 'PATCH',
    headers: {
      'Content-Type': 'application/json'
    },
    body: JSON.stringify({
      config: {
        cluster: {
          name: newName
        }
      }
    })
  })

  const data = await response.json()

  if (!data.status) {
    throw new Error(data.content?.message || data.content || 'Failed to rename Cluster')
  }

  return data
}
```

## 14. Troubleshooting

### Backend returns HTML instead of JSON

Likely cause:

- `INI_FILE` does not exist;
- `INI_FILE` is not readable;
- `TOKEN_FILE` is invalid;
- request hit the Flask 404 handler.

Recommended action:

```text
Check the backend logs and verify Luna configuration file access.
```

### Cluster update fails although Flask returns HTTP 200

Likely cause:

- Luna daemon rejected the payload;
- frontend sent incomplete or invalid Cluster data;
- shared `Rest.post_data()` does not support blank `name` for table-level Cluster operations;
- token retrieval failed;
- backend could not connect to the daemon.

Recommended action:

```text
Check response.data.status and response.data.status_code, not only the browser HTTP status.
```

### Rename fails with missing name

Likely cause:

- frontend did not send `config.cluster.name`;
- field is empty;
- payload uses the record-style rename field from another app, such as `newnetname` or `newbmcname`.

Correct payload:

```json
{
  "config": {
    "cluster": {
      "name": "newclustername"
    }
  }
}
```

### Shared `post_data()` issue

For Cluster, the backend calls `post_data()` with an empty record name. The shared method should allow this and produce the URL:

```text
/config/cluster
```

If the method was changed to require a non-empty `name`, add an exception for `table == "cluster"` or support table-level operations generally.
