# Luna2 Other Device Backend for Open OnDemand

Python backend service for managing Luna2 **Other Device** configuration from the TrinityX Open OnDemand interface.

This service sits between Open OnDemand and the Luna2 daemon. It exposes a small HTTP API that the future Vue.js frontend can call to list, create, update, clone, rename and delete `otherdev` records.

```text
TrinityX
  └── Open OnDemand
        └── Luna2 Other Device Python Backend
              ├── Flask API: /api/v1/...
              ├── Token handling for Luna2 daemon
              └── Luna2 daemon REST API
                    └── Other Device configuration

Future UI flow:
Open OnDemand page → Vue.js frontend → Python backend → Luna2 daemon
```

---

## 1. Purpose

The backend provides an Other Device management API for Luna2 `otherdev` objects inside TrinityX Open OnDemand.

It is responsible for:

- serving the Open OnDemand application shell;
- exposing Other Device API routes for the frontend;
- reading Luna daemon connection details from the Luna configuration file;
- retrieving and caching a Luna daemon API token;
- forwarding Other Device actions to the Luna2 daemon;
- returning a consistent frontend-friendly response where possible.

Other Device records define non-node devices known to Luna. These may include external appliances, development boards, infrastructure devices, lab systems, or any device that should be tracked by name, IP address, network and vendor information without being managed as a normal Luna node.

## 3. Configuration

The backend reads Luna daemon API settings from the Luna configuration file defined by `INI_FILE`.

The expected configuration section is:

```ini
[API]
USERNAME=<luna-api-username>
PASSWORD=<luna-api-password>
SECRET_KEY=<jwt-secret-key>
PROTOCOL=https
ENDPOINT=<luna-daemon-host>:<luna-daemon-port>
VERIFY_CERTIFICATE=true
```

The backend also uses a `TOKEN_FILE` to cache the JWT token received from the Luna2 daemon. The token file is written with permission mode `0600`.

Before processing requests, the backend validates that:

- the Luna configuration file exists;
- the Luna configuration file is readable;
- the token file path is valid.

If this validation fails, the backend returns the Open OnDemand `error.html` template rather than a JSON API response.

## 5. General response format

Most API endpoints return the following JSON envelope:

```json
{
  "status": true,
  "status_code": 200,
  "content": {}
}
```

| Field | Meaning |
| --- | --- |
| `status` | Boolean success indicator generated by the backend wrapper. |
| `status_code` | Luna daemon status code or backend-generated status code. |
| `content` | Data or error details returned by the Luna daemon or backend. |

Important frontend note:

The Flask route itself often returns HTTP `200`, even when the JSON body contains an error such as `status: false` and `status_code: 404`.

For the Vue.js frontend, do not rely only on the HTTP response code. Always check:

```js
if (response.data.status === true) {
  // show success box
} else {
  // show failure box using response.data.content
}
```

Exceptions:

- `GET /` returns HTML.
- `GET /api/v1/license` returns text/HTML, not the standard JSON envelope.
- configuration validation errors return `error.html`.
- unknown routes return `error.html` with HTTP `200`.

## 6. Other Device object structure

An Other Device record is expected under:

```json
{
  "config": {
    "otherdev": {
      "<other-device-name>": {
        "name": "<other-device-name>",
        "network": "<network-name>",
        "ipaddress": "<ipv4-address>",
        "ipaddress_ipv6": "<optional-ipv6-address>",
        "macaddress": "<optional-mac-address>",
        "vendor": "<optional-vendor>",
        "comment": "<optional-comment>"
      }
    }
  }
}
```

Example Other Device object:

```json
{
  "config": {
    "otherdev": {
      "sut": {
        "comment": "T25seSBmb3IgdGVzdA==",
        "ipaddress": "10.141.11.11",
        "ipaddress_ipv6": null,
        "macaddress": null,
        "name": "sut",
        "network": "cluster",
        "vendor": "EHL"
      }
    }
  }
}
```

The backend uses the first key below `config.otherdev` as the record name:

```python
name = next(iter(request_data["config"]["otherdev"]))
```

For predictable behaviour, send only one Other Device record per create, update, clone or rename request.

### Field notes

| Field | Type | Notes |
| --- | --- | --- |
| `name` | String | Other Device name. Should match the object key for add/update operations. |
| `network` | String | Luna network name where the device belongs, for example `cluster`. |
| `ipaddress` | String/null | IPv4 address for the device. |
| `ipaddress_ipv6` | String/null | Optional IPv6 address for the device. |
| `macaddress` | String/null | Optional MAC address. |
| `vendor` | String/null | Optional vendor or device family label, for example `EHL`. |
| `comment` | String/null | Optional operator note. The observed daemon response may store this as Base64-encoded text. |

Comment note: in the example response, `comment` is returned as `T25seSBmb3IgdGVzdA==`, which decodes to `Only for test`. The frontend should confirm whether comments are always Base64-encoded before automatically decoding them. If uncertain, display raw values in an advanced/details view and decode only when the value is valid Base64.

## 7.6 Clone Other Device

```http
POST /api/v1/clone
```

Clones an existing Other Device record in Luna2.

Internally calls:

```text
POST <luna-daemon>/config/otherdev/<other-device-name>
```

The backend derives `<other-device-name>` from the first key below `config.otherdev` and sends the payload to the daemon with `action="clone"`.

The exact payload required by the Luna daemon depends on daemon-side clone semantics. Based on the rename pattern, the payload should contain the source Other Device and a daemon-recognised field for the target clone name.

### Success message box

```text
Other Device cloned successfully.
```

### Failure message box

```text
Could not clone Other Device. Check the source device, target name and daemon validation message.
```

### Request body example

Use the field expected by the Luna daemon for the new clone name. If the daemon follows the same naming pattern as rename, the payload may look like this:

```json
{
  "config": {
    "otherdev": {
      "sut": {
        "newotherdevname": "sut-copy"
      }
    }
  }
}
```

If the daemon expects a full target object, use this shape instead:

```json
{
  "config": {
    "otherdev": {
      "sut-copy": {
        "comment": "Cloned from sut",
        "ipaddress": "10.141.11.21",
        "ipaddress_ipv6": null,
        "macaddress": null,
        "name": "sut-copy",
        "network": "cluster",
        "vendor": "EHL"
      }
    }
  }
}
```

### Success response example

The expected ideal backend response should be:

```json
{
  "status": true,
  "status_code": 201,
  "content": {
    "message": "Other Device sut was cloned successfully."
  }
}
```

### Failure response examples

No JSON payload:

```json
{
  "status": false,
  "status_code": 400,
  "message": "No JSON payload received"
}
```

Daemon validation error:

```json
{
  "status": false,
  "status_code": 400,
  "content": {
    "message": "Invalid request: otherdev sut could not be cloned"
  }
}
```

### Backend implementation caveat

The application route exposes `POST /api/v1/clone`, but the `Rest.post_data()` implementation must explicitly handle `action == "clone"`.

If the `Rest.post_data()` logic is still the same as the Network backend version, clone success may be reported incorrectly because only these actions currently have explicit success handling:

- `add` with daemon HTTP `201`;
- `update` with daemon HTTP `204`;
- `rename` with daemon HTTP `204`.

Recommended backend addition:

```python
elif response.status_code in [200, 201, 204] and action == "clone":
    self.response = {
        "status": True,
        "status_code": 200 if response.status_code == 204 else response.status_code,
        "content": {"message": f"{table.capitalize()} {name} is cloned successfully."}
    }
```

If the daemon returns a JSON body on clone, preserve that JSON in `content` instead of replacing it with a generic message.

# 8. Frontend handling guide

## 8.1 Standard JSON API handling

For most API endpoints, the Vue.js frontend should check the JSON body:

```js
const result = await apiCall()

if (result.data?.status === true) {
  showSuccess(result.data.content)
} else {
  showFailure(result.data?.content || 'Request failed')
}
```

Do not treat HTTP `200` as success by itself.

The backend may return:

```json
{
  "status": false,
  "status_code": 404,
  "content": {
    "message": "Invalid request: otherdev missing-device does not exist"
  }
}
```

with an outer Flask HTTP response of `200`.

## 8.2 Error message extraction

Recommended frontend message extraction:

```js
function getApiMessage(data, fallback = 'Request failed') {
  if (!data) return fallback

  if (typeof data.content === 'string') return data.content

  if (data.content?.message) return data.content.message

  if (data.message) return data.message

  return fallback
}
```

## 8.3 Comment handling in the UI

The observed Luna daemon response returns the `comment` field as Base64 in the supplied example.

Recommended frontend behaviour:

- treat `comment` as optional;
- safely detect whether the value is valid Base64 before decoding;
- avoid corrupting the value during edit/save cycles;
- if the backend/daemon expects Base64 on write, encode comments before submission;
- if the backend/daemon expects plain text on write, submit plain text and let the daemon normalise it;
- confirm the final daemon expectation before enabling edit-in-place for comments.

A safe display helper can follow this pattern:

```js
function displayComment(value) {
  if (!value) return ''

  try {
    const decoded = atob(value)
    return decoded || value
  } catch {
    return value
  }
}
```

| Action | After success | After failure |
| --- | --- | --- |

# 10. Backend behaviour notes

These details matter for frontend implementation.

1. The backend is a wrapper around the Luna2 daemon. It does not store Other Device data itself.
2. The backend retrieves daemon credentials from the Luna configuration file.
3. The backend requests a Luna daemon token and caches it in `TOKEN_FILE`.
4. If the cached token is invalid or expired, the backend requests a new token.
5. Create, update, clone and rename requests all call the Luna daemon with `POST` internally.
6. Delete calls the Luna daemon using the daemon-specific `_delete` route.
7. The route method exposed to the frontend may differ from the method used internally against the Luna daemon.
8. Most API routes return JSON, but the application shell, licence route and configuration errors return HTML/text.
9. The frontend should refresh `/api/v1/otherdevs` after add, update, clone, rename or delete actions.
10. The frontend should show daemon validation messages directly where possible because they explain the real reason for failure.
11. The backend currently assumes one `otherdev` object per create/update/clone/rename request.
12. The observed `comment` value may be Base64-encoded. Confirm encode/decode behaviour before finalising the Vue.js edit form.

# 11. Recommended frontend success and failure components

Every API action should expose two visible message areas.

## Success box

Use this for completed actions.

```text
Title: Success
Body: <action-specific success message>
Style: green/positive state
Behaviour: auto-dismiss after a few seconds, except for destructive actions where keeping it visible can help confirmation
```

## Failure box

Use this for validation, daemon, configuration or connection errors.

```text
Title: Request failed
Body: <daemon message or backend fallback message>
Style: red/error state
Behaviour: keep visible until the user closes it or retries
```

The failure box should prefer messages in this order:

1. `content.message`
2. `content` when it is a string
3. `message`
4. generic fallback message

# 13. Known limitations and improvement points

These are not blockers, but they are useful to know before connecting the Vue.js frontend.

- Some error responses are JSON, while others are HTML/text.
- Some Flask routes return HTTP `200` even when the body contains an error status.
- `rename` returns a missing-payload error without `status_code`.
- `404` pages are rendered as `error.html` with HTTP `200`.
- Create, update, clone and rename assume one Other Device object per request.
- The backend currently trusts the payload shape and passes validation mainly to the Luna daemon.
- If the `Rest.post_data()` implementation has not been updated for `action == "clone"`, the clone route may not return a correct success response even when the daemon accepts the request.
- The display name generated by `table.capitalize()` becomes `Otherdev`, not `Other Device`. This is harmless technically, but less polished for user-facing messages.
- The observed `comment` field may be Base64-encoded. The frontend should avoid accidental double-encoding or broken decoding.

For a cleaner frontend contract later, consider standardising all API errors as JSON under the same envelope:

```json
{
  "status": false,
  "status_code": 400,
  "content": {
    "message": "Human-readable error message"
  }
}
```

A cleaner display name helper can keep UI/backend messages readable:

```python
DISPLAY_NAME = "Other Device"
```

For future cleanup, the backend could also expose a normalised success message for frontend users while keeping the raw Luna daemon response available for debugging.
